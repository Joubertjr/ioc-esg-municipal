## Inventário

**Stack:** Node.js 20 + TypeScript strict + Express + Prisma ORM + PostgreSQL + Redis (backend); React 18 + Vite + Tailwind + Shadcn/ui (frontend).

**Componentes:**

- 15 coletores de dados: 7 via API REST em tempo real (IBGE, SICONFI, DATASUS, INPE, PNCP, ANA, SNIS-RS) + 7 estáticos via JSON (IEPS, INEP, SNIS, SISVAN, ANATEL, ANEEL, Convênios) + 1 estático TSE
- Services: ods/, simulator/, reports/, benchmarks/, recommendations/, agent/ (MDO), graph/, clustering/, ingestion/
- 11 rotas Express: auth, ods, simulator, reports, benchmarks, municipalities, recommendations, agent, agents, ingestion, graph
- Middleware: auth JWT, error-handler, request-id, request-logger
- Camada agêntica MDO: executive_report_service, hitl_queue_service, published_report_service, audit_service, agent_query_service
- Knowledge Graph: Entity + Relationship (TKG) — schema Prisma, sem testes dedicados observados
- Observabilidade: prom-client + Prometheus + Grafana + Alertmanager + IngestionRun/Log no DB

**Testes:**

- 65 arquivos de teste (64 passando, 1 skipped — siconfi_integration.test.ts)
- 1325 testes: 1320 passando, 5 skipped, 0 falhando
- Distribuição: unit (agentes, services, routes, middleware, utils), integration (api/, db/, apis/), e2e (6 specs Playwright)

**CI/CD:** GitHub Actions — tsc + lint + unit + integration + e2e Playwright + smoke 295 municípios SC + docker build; PR review automático via Claude; security audit semanal; API health check diário.

**IA/Agentes:** @huggingface/transformers v4.0.1 (embeddings, produção); MDO agent com HITL; eval:agent:fast em CI.

**Incertezas:** (1) Fitness function `no-circular-deps` não está wired no CI principal — detectada localmente apenas. (2) `eval:agent:fast` usa `--skip-integration`, sem chamadas LLM reais no CI.

### CRÍTICO

#### C-01 — protobufjs CVE (arbitrary code execution) em dependência de produção

**Dimensão:** G (Segurança e supply chain)

**Evidência:** `pnpm audit` — `protobufjs@7.5.4 < 7.5.5` via `@huggingface/transformers@4.0.1 > onnxruntime-web@1.25.0-dev > protobufjs@7.5.4`. `@huggingface/transformers` está em `dependencies` (produção) em `package.json:54`.

**CVE:** GHSA-xq3m-2v4x-88gg — Arbitrary code execution in protobufjs.

**Cenário de falha:** Se `onnxruntime-web` usa `protobufjs` para parsear arquivos `.proto` gerados por input externo, um atacante com acesso a carregar modelos pode executar código arbitrário. Risco real depende de como `@huggingface/transformers` é invocado em runtime.

**Impacto potencial:** Execução remota de código no container de produção.

**Recomendação:** Atualizar `@huggingface/transformers` para versão que dependa de `protobufjs >= 7.5.5`, ou usar `pnpm overrides` para forçar `"protobufjs": ">=7.5.5"` enquanto aguarda release upstream. Verificar se a funcionalidade de embeddings requer onnxruntime-web ou pode usar provider alternativo.

---

#### C-02 — Ciclo de importação mútuo estático: hitl_queue_service ↔ published_report_service

**Dimensão:** B (Arquitetura e modularidade)

**Evidência:**

- `backend/services/agent/hitl_queue_service.ts:6` — `import { publishExecutiveReportFromHitl } from "./published_report_service.js"`
- `backend/services/agent/published_report_service.ts:4` — `import { createHitlRequest } from "./hitl_queue_service.js"`

Ambos os imports são **estáticos e síncronos** — nenhum usa `await import()`. Isso cria um ciclo que o Node.js resolve com módulo parcialmente inicializado, podendo resultar em `undefined` em runtime dependendo da ordem de importação.

**Cenário de falha:** Se a inicialização do módulo A depende de um export de B que ainda não foi avaliado (porque B ainda está importando A), a função importada pode ser `undefined` no momento da chamada, causando `TypeError` em fluxos HITL.

**Impacto potencial:** Falha silenciosa no fluxo de publicação de relatório executivo — `publishExecutiveReportFromHitl` ou `createHitlRequest` retornando `undefined` em runtime.

**Recomendação:** Extrair a dependência compartilhada para um módulo intermediário. Por exemplo, mover `createHitlRequest` para um `hitl_persistence_service.ts` sem importar `published_report_service`, e ter `hitl_queue_service` orquestrar a chamada via injeção de dependência ou evento.

### ALTO

#### A-01 — axios 1.15.0 com vulnerabilidade high em dependência de produção

**Dimensão:** G (Segurança e supply chain)

**Evidência:** `pnpm audit` — `axios@1.15.0` em `dependencies` (`package.json:56`). Duas vulnerabilidades high:

- GHSA: `NO_PROXY` bypass via loopback subnet (RFC 1122) — fix em `>=1.15.1`
- Null byte injection via `AxiosURLSearchParams` — fix em `>=1.15.1` (low severity mas mesmo pacote)

`axios` é usado em todos os coletores de APIs governamentais (IBGE, SICONFI, DATASUS, etc.) via `backend/utils/http-client.ts`.

**Cenário de falha:** Em ambientes com proxy corporativo configurado via `NO_PROXY`, requisições a destinos que deveriam ser bloqueados podem vazar pelo proxy. Impacto reduzido em deploy Docker sem proxy, mas representa postura de segurança inadequada.

**Recomendação:** `pnpm update axios --latest` (atualizar para `>=1.15.1`). Executar testes de integração após atualização.

#### A-02 — Fitness function no-circular-deps não está no pipeline de CI

**Dimensão:** K (CI/CD e governança)

**Evidência:** `.github/workflows/main.yml` não contém nenhuma chamada a `pnpm madge:circular` ou ao script `quality/fitness-functions/no-circular-deps.sh`. A detecção dos 3 ciclos foi feita localmente — o CI não bloqueia regressões arquiteturais.

**Cenário de falha:** Um ciclo novo introduzido por feature futura não será detectado automaticamente, acumulando dívida arquitetural invisível.

**Impacto potencial:** O ciclo C-02 (hitl ↔ published_report) poderia ter sido detectado e prevenido se a fitness function estivesse no CI.

**Recomendação:** Adicionar step no job `ci` do `main.yml`:

```yaml
- name: Circular dependency check
  run: pnpm madge:circular
```

### MÉDIO

#### M-01 — Ciclos mistos nos outros dois pares (madge detecta, runtime tolera)

**Dimensão:** B (Arquitetura e modularidade)

**Evidência:**

- `ods_score_service.ts:183` usa `await import("../ingestion/ods_score_reader.js")` (dinâmico); `ods_score_reader.ts` usa `import type` estático de `ods_score_service.ts` — type-only import é erasado em runtime, ciclo inofensivo em JS.
- `simulator_service.ts:333` usa `await import("../agent/hitl_queue_service.js")` (dinâmico); `hitl_queue_service.ts:3-4` usa import estático de `simulator_service.ts` — o import dinâmico quebra o ciclo em runtime.

**Impacto potencial:** Baixo em runtime (dynamic imports garantem lazy resolution), mas madge os reporta como FAIL, poluindo o gate e mascarando ciclos verdadeiramente perigosos como C-02.

**Recomendação:** Refatorar `ods_score_reader` para não importar tipos de `ods_score_service` (mover tipos compartilhados para `shared/types/` ou módulo neutro). Para o ciclo simulator ↔ hitl, o padrão de dynamic import já é correto — considerar documentar como padrão intencional via comentário ou `.madgeignore`.

#### M-02 — siconfi integration test completamente skipped (5 testes)

**Dimensão:** F (Integrações, APIs e contratos)

**Evidência:** `tests/integration/agents/siconfi_integration.test.ts` — 5 tests skipped. SICONFI é a fonte de dados de FPM — o dado financeiro mais crítico da plataforma para os prefeitos.

**Cenário de falha:** Uma mudança no formato da resposta da API SICONFI não seria detectada automaticamente em CI. O parsing de código IBGE→SICONFI (7→6 dígitos) não tem cobertura de integração executada.

**Recomendação:** Implementar mock de HTTP (msw ou nock) para os endpoints SICONFI usados nos testes, substituindo os skips por testes com payload gravado (snapshot). Manter testes reais opcionais via variável de ambiente `SICONFI_LIVE_TEST=1`.

---

#### M-03 — Erro Prisma vazando em stdout de testes unitários

**Dimensão:** E (Efetividade dos testes)

**Evidência:** Durante `npx vitest run`, `tests/unit/services/ods_score_service.test.ts` produz no stdout:

```
prisma:error — Authentication failed against database server at `localhost`, the provided database credentials for `ioc` are not valid.
```

Os testes passam porque a falha é capturada via try/catch em `readOdsReportFromDatabase`, mas um teste unitário está fazendo uma chamada real ao banco PostgreSQL (que falha no ambiente local sem banco configurado).

**Impacto potencial:** Os testes unitários dependem silenciosamente do comportamento de fallback de um erro de infra. Se o banco estiver disponível com dados diferentes, o resultado do teste pode variar.

**Recomendação:** Em `ods_score_service.test.ts`, mockar o módulo `../../services/ingestion/ods_score_reader.js` com `vi.mock` para eliminar a dependência implícita de banco em testes unitários.

---

#### M-04 — Sem gate de cobertura mínima de testes no CI

**Dimensão:** K (CI/CD e governança)

**Evidência:** `main.yml` não contém `--coverage` nem threshold de cobertura. Não há percentual mínimo estabelecido.

**Impacto potencial:** Código crítico novo pode ser mergeado sem testes, sem detecção automática.

**Recomendação:** Adicionar `pnpm test:coverage --coverage` com `c8` ou `istanbul` e configurar thresholds no `vitest.config.ts` (sugestão: 80% para lines em `backend/services/`). Iniciar com threshold conservador para não bloquear CI atual.

**Evidência:** `backend/services/graph/` existe. Schema Prisma define `Entity` e `Relationship` com TKG. Não foi encontrado arquivo de teste em `tests/unit/services/graph_service.test.ts` durante a execução de vitest (o arquivo existe em `tests/unit/services/graph_service.test.ts` — 19k de tamanho mas não apareceu nos 64 arquivos que passaram). Verificação: o arquivo pode existir mas não estar no glob de testes.

**Recomendação:** Confirmar cobertura com `pnpm vitest --reporter=verbose | grep graph`. Se não coberto, priorizar testes de `findSynergies` e `findTradeOffs` (chamados pelo `simulator_service`).

#### B-02 — MDO/HITL com cobertura muito delgada

**Dimensão:** D (Cobertura por risco)

**Evidência:**

- `hitl_queue_service.test.ts`: 3 testes
- `published_report_service.test.ts`: 2 testes
- `audit_service.test.ts`: 2 testes
- `agent_query_service.test.ts`: 3 testes

O fluxo completo de aprovação HITL (approve → persist/publish → audit trail) não está coberto de ponta a ponta em nenhum teste observado.

**Recomendação:** Adicionar teste de integração cobrindo o fluxo completo: `POST /api/agent/hitl/:id/approve` → verificar que simulação foi persistida ou relatório publicado → verificar audit log.

### OBSERVAÇÃO

- **vitest UI server (critical vuln GHSA-5xrq-8626-4rwp)**: afeta apenas `vitest ui` — modo de desenvolvimento interativo, não o runner CI (`vitest run`). Sem impacto em produção. Atualizar `vitest` de `1.6.1` para `>=3.2.6` resolve, mas é breaking change major.
- **shell-quote (critical GHSA-w7jw-789q-3m8p)**: via `concurrently` (devDependency). Não exposto em produção.
- **xlsx (high vulns)**: é devDependency (`package.json:105`). Não incluído na imagem de produção.
- **Rate limiting desabilitado**: documentado em `security.md` como decisão do operador para fase pré-lançamento. Risco aceitável temporariamente.
- **`url.parse()` deprecated (Node.js)**: aparece no output do `pnpm audit`. Não é vulnerabilidade direta — é warning de depreciação.
